Part A — Tuples
01What Is a Tuple?▸
"Tuple and list are siblings — very similar. There is only one big difference: you cannot change the elements of a tuple. In simple words, a tuple is immutable, just like strings — and a list is mutable."

Core idea Think of a tuple as an immutable list. Everything you already know about lists (indexing, slicing, iteration, nesting) carries over — the one thing that changes is that once a tuple is created, it can never be edited again.

3 characteristics

  • Ordered — position matters, same as a list.
  • Unchangeable — cannot be edited once created.
  • Allows duplicates — repeated values are fine.

Plan for this topic (same shape as every data type so far): Creating → Accessing → Editing → Adding → Deleting → Operations → Functions.

Empty tuple uses round brackets () — the first visible tuple-vs-list difference (list used square brackets). A tuple can be homogeneous, heterogeneous, or even nested (a tuple inside a tuple). tuple('hello') converts any iterable into a tuple, splitting a string into its characters.

⚠ The single-item tuple trap
Writing t2 = (2) does NOT make a tuple — it just makes the integer 2 (parentheses here are read as grouping, not tuple syntax). Same for ("hello") — that's just a string. You must add a trailing comma: t2 = (2,) or t2 = ('hello',). Proven above by checking type(t2) → <class 'tuple'> only once the comma is there. This is one of the most common beginner mistakes with tuples.

Core idea Same two tools as strings and lists — this is the third time learning indexing/slicing, so nothing new mechanically: positive indexing left-to-right from 0, negative indexing right-to-left from -1, and slicing with start:stop:step.

Nested (2D) tuple access works exactly like 2D lists — chain the index brackets. t5 = (1, 2, 3, (4, 5)), so t5[-1] grabs the inner tuple (4, 5), then [0] grabs 4 from it.

t = (1,2,3,4,5)

t[-1:-4:-1]
(5, 4, 3)
★ The instructor's negative-step "hack"
"Whenever you take a negative step, always remember the left-side number must be greater. It's exactly the opposite for a positive step — there the left-side number must be smaller." That's why t[-1:-4:-1] works (−1 is "greater" moving right-to-left) — get the direction backwards and you'll silently get an empty result instead of an error.
04Editing, Adding & Deleting▸

Editing — not possible

print(t3)
t3[0] = 100
# immutable just like strings
(1, 2, 3, 4)

Adding — not possible

There is no .append(), .extend(), or .insert() for tuples — the whole family of "add" methods lists have simply doesn't exist here, for the same immutability reason.

Deleting — only the whole tuple, never a piece

print(t3)
del t3
print(t3)
(1, 2, 3, 4)
NameError — name 't3' is not defined
print(t5)

(1, 2, 3, (4, 5))
TypeError — 'tuple' object doesn't support item deletion
★ One-line summary
Editing doesn't work. Adding doesn't work. Deleting works only for the entire tuple (del t3 removes the whole variable) — never a single item inside it.

★ Rule of thumb for speed & memory
"Generally, immutable data types are faster and take less memory than mutable data types." Whenever a question compares two data types on speed or memory, decide based on which one is mutable vs immutable — immutable usually wins on both. The exact "why" (at the memory level) is deferred to the dedicated interview-questions session.

Proof — speed test

import time

L = list(range(100000000))
T = tuple(range(100000000))

start = time.time()
for i in L:
  i*5
print('List time',time.time()-start)

start = time.time()
for i in T:
  i*5
print('Tuple time',time.time()-start)
List time 9.853569507598877
Tuple time 8.347511053085327

Tuple iteration finished faster. The instructor notes the gap looks small here only because the operation per item (i*5) is trivial — with heavier processing per item, the gap would widen.

Proof — memory test

import sys

L = list(range(1000))
T = tuple(range(1000))

print('List size',sys.getsizeof(L))
print('Tuple size',sys.getsizeof(T))
List size 9120
Tuple size 8056

Proof — debugging safety (accidental aliasing)

a = [1,2,3]
b = a

a.append(4)
print(a)
print(b)
[1, 2, 3, 4]
[1, 2, 3, 4]
a = (1,2,3)
b = a

a = a + (4,)
print(a)
print(b)
(1, 2, 3, 4)
(1, 2, 3)
⚠ Why this matters
With the list, b = a makes b point at the same object — appending through a silently changes b too, a classic source of bugs. With the tuple, a = a + (4,) can't mutate the original — it builds a brand-new tuple and rebinds a to it, leaving b untouched. "Because nothing can change, there's less chance of mistakes — debugging is easier."
◆Why Use a Tuple? — The Branch/CGPA Story▸
✎ The instructor's analogy for when to reach for a tuple
Suppose you got placed at your own college as a web developer, building the college website. Your friend got an engineering branch he didn't want (say Electrical) but wants Computer Science — he was told "keep your CGPA above 8 in first year and you can switch branches." He tried hard, but hostel life got in the way: "everyone studies together only if everyone feels like it — if nobody feels like it, nobody studies." Despite the effort, he ends up with a CGPA of 6. Now he comes to you, the developer who built the results page, and asks you to just change his CGPA.

Question posed to the class: if the result data were stored in a list, could you change it? What if it were stored in a tuple?
  • Stored in a list → yes, it can be edited — dangerous, since anyone with access could tamper with it.
  • Stored in a tuple → no, it cannot be edited — safe, tamper-proof by design.
★ The actual rule to remember
"Whenever you're building a read-only application — where you'll only read data, never change it — prefer tuples. Where you're building something the user will change a lot, like a to-do list, use a list." (Instructor's own caveat: "not a perfectly accurate example, but it should make the concept clear.")
08Tuple Unpacking, Swapping & zip()▸

Basic unpacking

a,b,c = (1,2,3)
print(a,b,c)
1 2 3
a,b = (1,2,3)
print(a,b)
ValueError — too many values to unpack (expected 2)

The number of variables on the left must match the number of items on the right — "both sides must match."

The famous swap-without-a-temp-variable trick

a = 1
b = 2
a,b = b,a

print(a,b)
2 1
★ Why this is famous
In most other languages, swapping two variables needs a third temporary variable. Python's tuple unpacking does it in one line — "a syntax that helps you in many places instead of writing three lines the long way."

Partial unpacking with the star (*) operator

a,b,*others = (1,2,3,4)
print(a,b)
print(others)
1 2
[3, 4]

a takes the first value, b the second, and *others scoops up everything left over into a list. This pattern will show up "knowingly or unknowingly" many more times through the course.

zip() on tuples

# zipping tuples
a = (1,2,3,4)
b = (5,6,7,8)

tuple(zip(a,b))
((1, 5), (2, 6), (3, 7), (4, 8))
✎ zip() is a utility, not a standalone feature
"It's like a screwdriver — it has no job of its own, but it's useful as a tool for some other task, like opening up a TV or laptop." zip() pairs items from two iterables position-by-position; it's genuinely useful whenever you need to combine two sequences, as seen again later in dictionary comprehension.
★ Tuples, one-line summary
"Tuple is the sibling of list, with one big difference: immutability. Every READ operation you know from lists works the same on tuples — every WRITE operation simply doesn't."
Part B — Sets
09What Is a Set? — 4 Key Rules▸

Core idea A set is an unordered collection where every element is unique. Python borrowed this straight from the set theory taught in school math — "Python took the same math concept and turned it into a data type. That's it."

"If you remember these 4 things I'm about to tell you, you will never make a mistake with sets again."
  1. Unordered — the most important rule. Unlike lists/tuples (both ordered), a set has no fixed position for its items: {1,2,3} equals {3,2,1}.
  2. Mutable — you can add and remove items after creation.
  3. No duplicates — every element must be unique.
  4. Only immutable items allowed inside — the set container itself is mutable, but nothing mutable (a list, another set, a dict) can go inside it.

Sets are also the tool for real mathematical set operations: union, intersection, difference, symmetric difference.

◆ "Are 2D sets possible?" — a set containing a set
Posed directly to the class before revealing the answer. No. Sets are mutable, and only immutable things are allowed inside a set — so a set (itself mutable) can never go inside another set. Confirmed by code: {1, 2, {3, 4}} throws TypeError: unhashable type: 'set', which in plain words means "a mutable type can't live inside a set."

⚠ The {} gotcha — empty curly braces make a dict, not a set!
s = {} does not create an empty set — it creates an empty dictionary. Reason: sets and dictionaries share the same {} syntax, and Python gives empty {} the default meaning of "dictionary." The only correct way to make an empty set is the type-conversion function: s = set(). This trips up beginners regularly.

A populated set can be written directly with curly braces (no ambiguity once it's non-empty). A heterogeneous set can mix int, string, float, and even a tuple (tuples are immutable, so they're allowed). Creating from a list via set([1,2,3]), or from a list with repeats, automatically drops duplicates.

s1 = {1,2,3}
s2 = {3,2,1}

print(s1 == s2)
True
◆ Sets check content, not order — different from lists & tuples
{1,2,3} == {3,2,1} is True. "This doesn't happen with lists, this doesn't happen with tuples" — equality for those checks position too, but a set only checks its content.
◆ Why doesn't a set print items in the order you added them?
This comes down to hashing — a Data Structures & Algorithms concept that decides which position each item lands in internally. "We have zero control over it." How hashing itself works is explicitly outside the scope of this session, but it's why a set's printed order looks scrambled compared to insertion order.
11Accessing, Editing, Adding & Deleting▸

Accessing — not possible

s1 = {1,2,3,4}
s1[0:3]
TypeError — 'set' object is not subscriptable

No positive indexing, no negative indexing, and therefore no slicing either — all for the same reason: sets are unordered, so there is no "first item" to point at.

Editing — not possible

s1 = {1,2,3,4}
s1[0] = 100
TypeError — 'set' object does not support item assignment

Same root cause: editing relies on indexing to locate a slot, and indexing doesn't exist here.

Adding — allowed!

S = {1,2,3,4}
# add
# S.add(5)
# update
S.update([5,6,7])
print(S)
{1, 2, 3, 4, 5, 6, 7}

.add(x) adds one item — exactly where it lands is decided by hashing, not you. .update([...]) adds several items at once, "just like append/extend on a list."

◆ Why do both remove() and discard() exist?
A viewer asked this directly. "Generally this happens because of different Python versions — one version had a feature, then it was improved in a later version, but the older one wasn't removed because a lot of company codebases still use it." Practical guidance: remove() is useful for catching errors early (it tells you something's wrong — relevant once you learn Exception Handling), while discard() stays silent. ⚠ pop() isn't fully predictable

★ The plain method vs the _update method

14Frozenset▸
"Frozen set is the sibling of set — an immutable version of a set object."
# create frozenset
fs1 = frozenset([1,2,3])
fs2 = frozenset([3,4,5])

fs1 | fs2
frozenset({1, 2, 3, 4, 5})
◆ Which set operations work on a frozenset?
Posed as a quick yes/no to the class. All of union, intersection, difference and symmetric difference work, because they're all READ operations — they don't change the set, only report a computed result. What does not work: pop(), remove(), discard(), update(), add() — every operation whose whole job is to change the set, since a frozenset can never change.
★ Meta-lesson
"If you understand sets well, apply common sense and you'll figure out on your own which function works on a frozenset and which doesn't." Frozen set = immutable version of set, nothing more. 
# When to use
# 2D sets
fs = frozenset([1,2,frozenset([3,4])])
fs
frozenset({1, 2, frozenset({3, 4})})
◆ Are 2D frozensets possible?
Yes — a frozenset can contain another frozenset, since frozensets are immutable and therefore satisfy "only immutable items allowed inside." This is exactly the opposite of a regular set, which can never contain another set. (A plain list still can't go inside a frozenset either — lists are always mutable.)

When to use: a frozenset for read-only, "ready-made" data you'll never change; a regular set when the application expects the data to keep growing or changing.

15Set Comprehension▸

Exactly the same idea as list/tuple comprehension — "nothing different." Curly braces instead of square ones, and duplicates automatically collapse.

# examples

{i**2 for i in range(1,11) if i>5}
{36, 49, 64, 81, 100}

Loop over 1..10, keep only values where i > 5, and store i**2 for each. Same filter-then-transform shape as list comprehension from the previous session — set comprehension just wraps it in {}.

With this, sets are done: unordered, mutable, unique, immutable-contents-only — plus their operations, functions, frozenset sibling, and comprehension syntax.
Part C — Dictionary
16What Is a Dictionary? — 4 Key Rules▸
"A very, very powerful data type" — used constantly in general programming and heavily in Data Science; "going forward when we study NumPy and Pandas, you'll see we use dictionaries a lot."

Core idea A dictionary is a collection of key-value pairs, used to store data like a map — different from every data type so far, which each hold a single item per slot. Also called a "Map" or "Associative Array" in other languages.

dict = { 'name' : 'nitish' , 'age' : 33 , 'gender' : 'male' }

4 rules to never get confused

  1. Mutable — items can be changed, deleted, and new key-value pairs added.
  2. Indexing has no meaning — there is no "give me the first key-value pair" by position.
  3. Keys can't repeat — every key must be unique.
  4. Keys can never be mutable — no list, set, or dict as a key. Values have no such restriction — anything can be a value.

Plan for this topic: Create → Access → Add → Remove → Edit → Operations → Functions.

✎ The 2D dictionary is literally what JSON looks like
The s example (name, college, sem, and a nested subjects dict of marks) is called a 2D dictionary — a dictionary inside a dictionary. "If you've ever heard of JSON, JSON actually follows this exact format." Later, when fetching data from APIs, that data arrives as nested dictionaries just like this.

★ The 1D → 2D rule repeats everywhere
"Whatever you learned for a 1D dict applies exactly the same in 2D, just one level deeper — apply a little common sense and you won't make mistakes." Accessing, adding, removing and editing nested values is just chaining the same operations you already know.

⚠ Membership and iteration both act on keys, not values
'name' in s checks whether 'name' is a key — membership never looks at values. A plain for i in d loop iterates over the keys only; to print values alongside, you need d[i] inside the loop, as shown above.

.items() is the one that matters most going forward — it turns the dict into a list of (key, value) tuples, and it's the workhorse behind dictionary comprehension next.

# update
d1 = {1:2,3:4,4:5}
d2 = {4:7,6:8}

d1.update(d2)
print(d1)
{1: 2, 3: 4, 4: 7, 6: 8}

.update() merges another dict in permanently — matching keys get overwritten with d2's value (key 4: 5 → 7), and any new keys get added (key 6).

20Dictionary Comprehension▸

Core idea Same underlying pattern as list/tuple/set comprehension. General shape: {key: value for variable in iterable}.

1. Squares dictionary

# print 1st 10 numbers and their squares
{i:i**2 for i in range(1,11)}
{1: 1, 2: 4, 3: 9, 4: 16, 5: 25, 6: 36, 7: 49, 8: 64, 9: 81, 10: 100}

2. Transform an existing dict's values (km → miles)

distances = {'delhi':1000,'mumbai':2000,'bangalore':3000}
{key:value*0.62 for (key,value) in distances.items()}
{'delhi': 620.0, 'mumbai': 1240.0, 'bangalore': 1860.0}

This is exactly where .items() earns its keep — unpacking each (key, value) pair directly inside the comprehension.

3. Build a dict from two lists with zip()

days = ["Sunday", "Monday","Tuesday","Wednesday","Thursday","Friday","Saturday"]
temp_C = [30.5,32.6,31.8,33.4,29.8,30.2,29.9]

{i:j for (i,j) in zip(days,temp_C)}
{'Sunday': 30.5, 'Monday': 32.6, 'Tuesday': 31.8, 'Wednesday': 33.4,
'Thursday': 29.8, 'Friday': 30.2, 'Saturday': 29.9}

4. Filter with an if condition

products = {'phone':10,'laptop':0,'charger':32,'tablet':0}

{key:value for (key,value) in products.items() if value>0}
{'phone': 10, 'charger': 32}

Out-of-stock items (0 quantity) get filtered out entirely — only phone and charger survive.

5. Nested comprehension — multiplication tables

# Nested Comprehension
# print tables of number from 2 to 4
{i:{j:i*j for j in range(1,11)} for i in range(2,5)}
{2: {1: 2, 2: 4, ..., 10: 20},
3: {1: 3, 2: 6, ..., 10: 30},
4: {1: 4, 2: 8, ..., 10: 40}}
✎ How the instructor traced this live
Outer loop picks i=2 → forms key 2 → for that key's value, an entire inner comprehension runs, looping j from 1 to 10 and computing i*j each time, building the nested dict {1:2, 2:4, ..., 10:20} → inner loop finishes → outer loop moves to i=3 → repeats. He walked through this using Python Tutor (a visualizer), noting "this isn't something you understand by explanation alone — it's something you understand by watching it execute." Advice: "grab pen and paper, work through it, and you'll get it."
◆ Should you actually write comprehensions like this in real code?
Instructor's honest personal take: "Personally I don't write it, because it can hurt code readability." Dense comprehensions are confusing in a team setting — "some people are comfortable with it, some aren't, so it's better to avoid it" in production/collaborative code. He still teaches it because "going forward you'll read other people's code, and code online — so you shouldn't be confused when you encounter it." Learn to read it fluently, even if you choose not to write the nested versions yourself.
★60-Second Cheat Sheet▸
Tuple = immutable list

Same behavior as lists, minus every write operation

Single-item tuple

Needs a trailing comma: (2,) not (2)

Tuple advantages

Faster, less memory, safer to debug — but fewer built-ins

Swap trick

a,b = b,a — no temp variable needed

Set = unordered, unique

Mutable container, but only immutable items allowed inside

Empty {} trap

{} makes a dict, not a set — use set()

Set ops

| union · & intersection · - difference · ^ symmetric diff

remove vs discard

remove errors if missing · discard stays silent

Frozenset

Immutable set — all read ops work, all write ops don't

Dict = key-value pairs

Keys unique & immutable · values unrestricted

Access a dict

d['key'] or d.get('key') — never by position

Membership & iteration

Both act on keys only, not values

.items()

Turns a dict into (key, value) tuples — powers dict comprehension

Comprehension shape
